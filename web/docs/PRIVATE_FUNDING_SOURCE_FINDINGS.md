## What the sources establish

### Ring initialization / `ring_config`

A custom Ring is a separately deployed Solana program. It controls notes carrying its program ID; SPP will accept its ring operations only when the ring's `ring_auth` PDA signs. The custom Ring's `Initialize` CPI creates the SPP `ring_config`, then configures its own roles/auditor/mode and (for policy Rings) policy. The SPP `create_ring_config` instruction is permissionless, but the ring program must invoke it signed by its canonical `[b"ring_auth"]` PDA. SPP initializes `activated` from `protocol_config.ring_activation_is_permissionless`; otherwise the configured `ring_creation_authority` must call `set_ring_activation`. See [SPP create](https://github.com/helius-labs/zolana/blob/b99ba45aa76029f8e89a4004725b9b3a6580a1ab/programs/shielded-pool/src/instructions/ring_config/create.rs), [governance activation](https://github.com/helius-labs/zolana/blob/b99ba45aa76029f8e89a4004725b9b3a6580a1ab/programs/shielded-pool/src/instructions/ring_config/set_activation.rs), and [custom Ring init](https://github.com/helius-labs/custom-privacy-rings/blob/cc21e141c65e845e61dca3418f2b1be3815f51f7/cli/src/commands/ring/init.rs).

`zolana-ring new` writes `ring.toml` (program ID, role key paths, target, endpoints, mode, and optional policy). `zolana-ring deploy` deploys the program; `zolana-ring init` requires the program's upgrade authority to sign the one-time `Initialize`, and a funded policy authority signs role/policy setup. Policy settings are actual rule-table rows and list sources, not a “make default Ring anonymous” flag. See [custom-ring README](https://github.com/helius-labs/custom-privacy-rings/blob/cc21e141c65e845e61dca3418f2b1be3815f51f7/README.md), [empty policy example](https://github.com/helius-labs/custom-privacy-rings/blob/cc21e141c65e845e61dca3418f2b1be3815f51f7/examples/empty-policy/ring.toml), and [policy model](https://github.com/helius-labs/zolana/blob/9e36d7f3f24c616fe2c962b3efa1851c96ad94c9/docs/ring-policy.md).

Read-only devnet observations made by the parent agent with the already-configured key: the protocol config decodes with `ringActivationIsPermissionless: true`; four fetched RingConfig accounts were 69 bytes and activated, all with `ringAuthorityTransactIsEnabled: false`. That switch controls the separate ring-authority/delegate rail; normal owner-authorized anonymous EdDSA spends use `ring_transact`. This is evidence of SPP Ring registration being live, not evidence that a particular anonymous custom-ring program, ring RPC, or USDC route is provisioned.

### Anonymous transfer construction and who pays

Zolana `main` has a real TS SDK method, `SprClient.proveAnonymousRingTransact`, which accepts proof inputs, ring program ID, owner authorization and key authority, and produces an `anonymousRingEddsa` instruction. It supports signer or previously prepared signature data. [`anonymous-ring-request.test.ts`](https://github.com/helius-labs/zolana/blob/9e36d7f3f24c616fe2c962b3efa1851c96ad94c9/sdk-libs/ts/test/anonymous-ring-request.test.ts) asserts the anonymous request sent to the prover and checks the encoded selector; it explicitly uses stubbed `fetch`, synthetic tree proofs and a fixture vector. It is a serialization/client contract test, **not** a successful real proof, custom Ring policy verification, transaction submission or relayer test. See [client method](https://github.com/helius-labs/zolana/blob/9e36d7f3f24c616fe2c962b3efa1851c96ad94c9/sdk-libs/ts/src/client/client.ts#L866-L900) and the [request fixture](https://github.com/helius-labs/zolana/blob/9e36d7f3f24c616fe2c962b3efa1851c96ad94c9/test-vectors/anonymous_ring_eddsa_request.json).

The actual custom-ring code is stronger evidence: its TS live suite builds an anonymous Ring, registers/enrolls members, creates an anonymous deposit, and runs either (a) a direct proof plus a separate fee payer or (b) `prepareRingTransferRelay` → quote → signed relay request → Ring RPC pays/proves/submits. The live test then confirms, audits the hidden sender and amount, syncs sender/recipient, and verifies notes. [`ring-anonymous.live.test.ts`](https://github.com/helius-labs/custom-privacy-rings/blob/cc21e141c65e845e61dca3418f2b1be3815f51f7/sdk-libs/ts/test/e2e/ring-anonymous.live.test.ts). The Rust suite has matching real program-test coverage, including [a relayed anonymous payment](https://github.com/helius-labs/custom-privacy-rings/blob/cc21e141c65e845e61dca3418f2b1be3815f51f7/program-tests/custom-ring/tests/ring/relay.rs#L15-L61) and [a hidden-owner CLI transfer with a separate fee payer](https://github.com/helius-labs/custom-privacy-rings/blob/cc21e141c65e845e61dca3418f2b1be3815f51f7/program-tests/custom-ring/tests/ring/anonymous.rs#L1-L94).

An anonymous custom Ring thus does not make its recipient unable to identify the sender: the Ring RPC holds the inputs needed to relay/prove, and the Ring auditor can open activity by design. Public-chain anonymity is distinct from operator/service privacy. An anonymous public-balance deposit remains visibly linked to source, destination/tag, token and amount. For a first test, use dummy devnet USDC only after confirming which SPL mint/interface the target Ring accepts.

### Feature gate and prover availability

The zolana program has an explicit `confidential-eddsa` feature, off in `just build-programs`; `just build-test-programs` opts into it. The gate applies to circuits with an in-proof `eddsa_owner_pk`, specifically `ConfidentialEddsa`, by matching `transfer_confidential_eddsa_*` key hashes. `AnonymousRingEddsa` has no `eddsa_owner_pk`; `circuit_enabled` instead accepts it when a verifying key exists. Therefore the compile-time **confidential-eddsa gate is not the blocker for the anonymous-ring circuit**. SPP still validates circuit type/key and ring activation. See [feature metadata / admission](https://github.com/helius-labs/zolana/blob/b99ba45aa76029f8e89a4004725b9b3a6580a1ab/programs/shielded-pool/src/circuit_features.rs), [feature docs](https://github.com/helius-labs/zolana/blob/b99ba45aa76029f8e89a4004725b9b3a6580a1ab/program-libs/feature-gate/README.md), and [circuit validation](https://github.com/helius-labs/zolana/blob/b99ba45aa76029f8e89a4004725b9b3a6580a1ab/programs/shielded-pool/src/instructions/transact/processor.rs).

The client can use Helius's current hosted devnet proof path: the official examples create `SprClient` with a Helius devnet RPC URL and `SignedTeePolicy.forNetwork("devnet")`, and route indexer/prover requests through the RPC host's `/v1/spr` endpoint. The parent agent has verified `attestProver()` against `aws-nitro` and `checkProverProvingKeys()` against 136 runtime keys through the encrypted, attested endpoint. That clears a previous concern based on unauthenticated metadata, but it is still not a proof that anonymous ring circuits work: `checkProverProvingKeys()` verifies the signed runtime key set, not a custom-ring proof or its on-chain verifier. Custom-Ring source also provides its own Go prover, ring indexer and Ring RPC and uses those in its local e2e. Run an actual anonymous-ring proof/settlement against the chosen deployed program before treating either hosted or local setup as verified. API setup is shown in [official TS example config](https://github.com/helius-labs/privacy-ring-examples/blob/9e5d69ade7e0c107a2929306d3b758a8969e1089/typescript-client/src/lib.ts#L88-L126).

### Runnable local experiment

The custom repo provides a purpose-built recipe, rather than requiring someone to assemble random services:

```bash
git clone --recurse-submodules https://github.com/helius-labs/custom-privacy-rings.git
cd custom-privacy-rings
just check-all && just test-hermetic
just test-custom-ring-validator 'test(a_relayed_anonymous_payment_reaches_its_recipient)' --features proofs
```

The last command is implemented by `just test-custom-ring-validator` and starts a local validator, local Photon, custom-ring indexer, the custom Go prover with pinned keys, and a test Ring RPC; its test deposits, relays, and verifies the hidden-owner transfer. A full TypeScript integration route is `just test-ts-e2e`, which creates fresh custom rings and runs the anonymous TS live suite with validator, Photon, ring indexer, prover, and Ring RPC (resource-intensive, builds many artifacts). See [just recipes](https://github.com/helius-labs/custom-privacy-rings/blob/cc21e141c65e845e61dca3418f2b1be3815f51f7/justfile#L158-L165) and [local stack recipe](https://github.com/helius-labs/custom-privacy-rings/blob/cc21e141c65e845e61dca3418f2b1be3815f51f7/justfile#L340-L385). `just test-custom-ring-validator` is the smallest concrete full-chain experiment. It is not a no-build command: it fetches pinned proving keys and builds several components/toolchains.

The generic zolana `zolana dev start` / `docker compose -f docker/docker-compose.yml up -d` only starts standard SPP, Photon, and the default prover stack; it does **not** deploy a custom Ring, run the ring indexer, or expose Ring RPC. Docker's published compose service graph contains Photon, Postgres, Redis, and the zolana prover, while the custom localnet recipe separately starts ring-indexer and ring-rpc. See [`docker/README.md`](https://github.com/helius-labs/zolana/blob/9e36d7f3f24c616fe2c962b3efa1851c96ad94c9/docker/README.md) and custom [`just ring-localnet`](https://github.com/helius-labs/custom-privacy-rings/blob/cc21e141c65e845e61dca3418f2b1be3815f51f7/justfile#L340-L385).

## Brobets feasibility and gaps

**There is a credible, reproducible public-source local experiment path for anonymous custom-Ring private transfers and relayed fee payment.** The custom-ring code is actively maintained and includes both runtime localnet suites and a dedicated ring prover/indexer/relay implementation. This materially improves on the SDK-only finding.

That does **not yet prove** the exact Brobets flow: public/external USDC deposit → private USDC balance → buy 1+ BB → redeem BB into private USDC. No source reviewed shows a Brobets BB accounting integration, deployed USDC custom Ring, or a real end-to-end test that backs 1 USDC per BB while charging 1+fee. The live parent probe establishes devnet SPP and HTTP availability, but not a matching hosted ring prover, ring RPC/policy deployment for Brobets, USDC support, real proof, or complete cost coverage. The immediate experiment should use the custom repo's local route, pin an SPL test mint, and separately measure deposit/withdraw visibility, relay/proof/base fees, ATA/interface creation and persistent account rent. Its built-in anonymous tests currently use SOL and are protocol proof, not USDC economics or production readiness.
